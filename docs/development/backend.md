# Backend (`slunk-be/`)

> Keep this page up to date: any change to the backend's stack, structure, scripts or conventions updates it in the same change.

The backend has phases 0 to 2:
- the database connection, the migration runner and the baseline migration;
- a GraphQL server with a `health` query;
- the media context: registering files, browsing the library on disk, serving the files' bytes, and file links;
- the catalog context: artists, labels, releases with their formats, media and labels, tracks, credits, and suggestions for importing a folder.

## Stack

| Piece | Choice |
|---|---|
| Runtime | Node 26, which runs the `.ts` files directly: there's no build step |
| HTTP + GraphQL | Express 5 and Apollo Server 5 (`@as-integrations/express5`), on `graphql` 16 |
| Database | SQLite through better-sqlite3, queried with Kysely |
| Types | kysely-codegen for the database, graphql-codegen for the resolvers |
| Batching | DataLoader, for the related rows a page shows |
| Audio | music-metadata, which reads durations and embedded tags |

Two versions are held back on purpose:
- `better-sqlite3` stays on 12, because kysely-codegen supports nothing newer.
- `graphql` stays on 16, which Apollo Server 5 requires.

## Configuration

Every npm script loads `slunk-be/.env` if it exists (`node --env-file-if-exists=.env`).

| Variable | Meaning |
|---|---|
| `SLUNK_DB` | Required. The database file. A relative path resolves from `slunk-be/`. Its folder must already exist. |
| `PORT` | The server's port. Default `4000`, which the frontend's Vite proxy expects. |

The server listens on `127.0.0.1` only, so nothing else on the network can reach it. It also refuses (403) any request whose `Host` isn't `localhost`, `127.0.0.1` or `[::1]`. Without that, a web page could point a domain it controls at 127.0.0.1 (DNS rebinding) and read the API, which can list any folder on the disk.

In development, `SLUNK_DB` points into `dev-library/`. Put sample music files and images there to register them. Never point it at a real music library.

## Contexts

The domain lives in contexts, like Phoenix's (design §6). Each one is a factory in `src/slunk/` that takes the repositories it needs and returns plain functions:

- **The context** declares the repository interfaces it needs, next to it: `src/slunk/media/repository.ts` declares `FilesRepository` and `FileLinksRepository`, and `src/slunk/catalog/repository.ts` declares `CatalogStore`, every repository the catalog uses.
- **`src/repo/`** implements them for SQLite. `createStore(db)` builds them all over one connection.
- **`src/server.ts`** wires them together once, at startup: `createMedia({ files, fileLinks, library })`, then `createCatalog({ store, media })`. A context can call another one: the catalog asks media to read and register files.
- **Resolvers** only call context functions. The one exception is `health`, which is about the backend itself and asks the repo directly.

Repositories turn rows into the context's own types: `snake_case` columns become `camelCase` fields (`size_bytes` → `sizeBytes`), and 0/1 flags become booleans. They also set `updated_at` on every update.

**Transactions.** `store.transaction(fn)` runs `fn` with repositories bound to one transaction, so a mutation that writes several tables writes all of them or none. Inside a transaction, nested calls join it. Reading files (hashing, durations) happens before the transaction starts, so the write lock is never held during disk I/O. `media.prepareFiles(paths)` reads files without writing anything, and `media.insertPrepared(tx, prepared)` registers them inside the transaction. That's how saving a release's tracks registers new files and creates their tracks in one go, and leaves no file registered if it fails.

**Text** is trimmed before it's saved, so " Rock " is saved as "Rock". The database's CHECKs still reject anything left empty.

**Errors** meant for the user are plain `Error`s with a readable message ("There's no file at …", "The release still has 3 tracks. Delete them first."). The triggers' messages pass through as they are. `slunk_web/errors.ts` rewrites SQLite's constraint errors into words a form can show: `UNIQUE constraint failed: tracks.file_id` becomes "That file is already a track's audio". GraphQL returns the message as is.

## The media context

`src/slunk/media.ts` registers files and reads the library. It never writes to the user's files: `src/slunk/media/library.ts` only reads them.

- **Paths** are relative to the database's folder, and normalized (design §4.1). The folder itself is `""`, and paths above it start with `../`.
- **Browsing** (`folder`) lists a folder's subfolders and the files directly inside, following symlinks. Each subfolder says whether it, or a folder inside it, holds registered files. That's an index range on `files.path`, and it also works for folders above the database's folder.
- **Scanning** (`folderFiles`) lists every file in a folder and its subfolders. It doesn't follow symlinked folders, so a link loop can't make it run forever.
- **Left out of both:** hidden files and folders (names starting with `.`, like `.DS_Store`), and Slunk's own files: the database, its `-wal`/`-shm`/`-journal` files and `slunk-backups/`.
- **Types** come from the extension, in `file_types.ts`:
  - `music`: aac, aif, aiff, alac, ape, dff, dsf, flac, m4a, mp3, mpc, oga, ogg, opus, wav, wma, wv;
  - `image`: avif, bmp, gif, heic, jpeg, jpg, png, svg, tif, tiff, webp;
  - `other`: everything else.
- **Registering** reads each file's size, mtime (in whole seconds) and SHA-256 (lowercase hex), streaming the file through the hash. Paths already registered are returned as they are.
- **Updating** changes the type, or the path, to relink a file that moved. A new path is read again, and it can't be one another file is registered at.
- **Deleting** removes only the record, and fails while anything uses the file: a track's audio, a cover, a picture or a file link. The error says what uses it.
- **File links** connect images and other files to releases, artists and tracks, each with an optional note. Saving an owner's links replaces them all.
- **Audio** (`audio.ts`) reads a file's duration and embedded tags with music-metadata. A file it can't parse has no duration and no tags.

### Serving files

`GET /raw/files/:id` (`files_controller.ts`) sends a registered file's bytes, read-only, for viewing and playback. Express sets the content type from the extension, and answers Range requests, so audio can seek. An unknown id, or a file missing on disk, gets a 404.

The path is under `/raw` so it can't collide with the frontend's `/files` pages ([design Appendix C](../design/1_introduction.md#appendix-c-file-bytes-are-served-under-raw)).

## The catalog context

`src/slunk/catalog.ts` holds what the user catalogs: artists, labels, releases, tracks, credits, and the three lists the user manages (release formats, release media, credit roles).

- **Lists** share one repository and one set of functions (`listItems`, `createListItem`, …), with a `kind`. Names are unique ignoring case.
- **Release dates** are typed as `2006`, `2006-01` or `2006-01-10`, which also sets the precision (`catalog/dates.ts`). They're stored at midnight UTC on the first unknown day, and returned with only their known parts. An impossible date, like `2013-02-30`, is refused.
- **A release's artists, labels, formats and media** are saved as ordered lists of ids, replacing the old ones. The order is `position` for artists and labels, and insertion order for formats and media.
- **A release's tracks** are saved as a whole list (`setReleaseTracks`):
  - rows with an id update those tracks;
  - rows with a `fileId` or a `path` create tracks, registering paths first;
  - tracks left out are deleted, but their files stay registered.

  Before saving, the release's track numbers are shifted out of the way, so swapping two numbers can't trip the unique (release, disc, number) index.
- **Durations** are read from the audio file when a track is created, or when its file changes.
- **Track artists** are the track's own performers. Features are kept apart, and an artist can't be both on one track.
- **Who performs a track** follows design §4.3:
  - its own non-featured artists;
  - on a regular release with none, the release's artists;
  - on a various-artists release, only its own, or nobody.
- **Credits** are an artist with a role, in display order. Saving a release's credits replaces them, and its tracks' credits too.
- **Deletes** check what blocks them first, and the error says what does: "The artist is still used: release artist on 1 release, credited 2 times". Each entity's `blockers` field gives the same reasons ahead of time, for the delete dialog.
- **Import suggestions** (design §7.9) only read the folder:
  - `suggestRelease(folder)`: the most common album, date and album artist tags, or else the folder's name. Also the releases with that title already, and how many audio files, images and other files the folder holds.
  - `suggestTracks(folder)`: a row for each audio file, with disc, number and title from its tags. Without tags, they come from the path: `CD2/03 Title.flac` is disc 2, track 3, "Title".

  The resolvers pair tag names with the artists that have exactly that name, ignoring case.

## The database

### Connection

`openDb()` in `src/repo/db.ts` opens the app's connection. It sets `foreign_keys = ON`, `journal_mode = WAL` and `busy_timeout = 5000`, and fails if the database doesn't exist yet (`migrate` creates it). The server closes the connection on `SIGINT` and `SIGTERM`, which removes the `-wal` and `-shm` files.

Slunk writes only next to the database: the database file itself, its `-wal`/`-shm` files while it's open, and `slunk-backups/`.

The schema is described in [reference/database.md](../reference/database.md).

### Running migrations

The runner is `src/repo/migrator.ts`. `migrate` does the following:

1. Opens its own connection with foreign keys off, so a table rebuild can't cascade deletes.
2. Compares the migration files with the `migrations` table. It fails if an applied migration's file is missing, or if a pending file sorts before the last applied one.
3. If anything is pending, backs the database up with `VACUUM INTO` to `slunk-backups/slunk-<timestamp>.db`, next to the database. A database that didn't exist yet isn't backed up. Two backups in the same second get a `-2`, `-3`, … suffix.
4. Starts `BEGIN IMMEDIATE`, which takes the write lock, so the server and the CLI can't interleave. It reads what's pending again, then runs each `up` and records it in `migrations`, which it creates the first time.
5. Runs `PRAGMA foreign_key_check`, and rolls back if any row breaks a foreign key.
6. Commits.

So all pending migrations apply together or not at all. After a failure, the database is as it was, and the backup is still there.

`rollback` works the same way, running `down` for the last *n* migrations, newest first.

The server runs `migrate` every time it starts, so users never migrate by hand. `db:migrate`, `db:rollback` and `db:reset` then regenerate `src/repo/db_types.ts` with kysely-codegen. The server doesn't.

### Writing a migration

1. `npm run db:gen -- add_track_tags` creates `priv/repo/migrations/<timestamp>_add_track_tags.ts`, with empty `up` and `down` functions that take a `Kysely<unknown>`.
2. Write `up` with Kysely's schema builder:
   - End every table with ``.modifyEnd(sql`strict`)``.
   - Declare ids `.primaryKey().notNull()`, adding `.autoIncrement()` for entity tables. `NOT NULL` changes nothing in SQLite, but kysely-codegen needs it to type ids as `number`.
   - Name indexes `<table>_<columns>_index`, as the baseline does.
   - Use raw `sql` for triggers and for inserting rows. A migration has no DB types to build typed queries with.
3. Write `down` so it undoes `up`, or make it throw an explicit "irreversible" error.
4. `npm run db:migrate`, then `npm run db:rollback` and `npm run db:migrate` again, to check that both directions work.
5. Update [reference/database.md](../reference/database.md).

The rules:
- Never edit a migration once it has been committed. Write a new one.
- A migration runs inside the runner's transaction, so it must not start its own (`db.transaction()`).
- Migrations don't import app code. App code changes over time, and a migration must not. The exception is `src/repo/rebuild_table.ts`, which is part of the migration system.
- Starter rows, like the first credit roles, are inserted by migrations, and nothing may depend on them. Sample data goes in `priv/repo/seeds.ts`.

### Changing an existing table

SQLite's `ALTER TABLE` only adds, renames and drops columns. Changing a column's type, CHECK, default or foreign key means rebuilding the table, with `rebuildTable()` from `src/repo/rebuild_table.ts`:

```ts
import { type Kysely, sql } from "kysely"
import { rebuildTable } from "../../../src/repo/rebuild_table.ts"

export async function up(db: Kysely<unknown>): Promise<void> {
  await rebuildTable(db, "artists", {
    // The complete new definition
    define: (table) =>
      table
        .addColumn("id", "integer", (col) =>
          col.primaryKey().autoIncrement().notNull()
        )
        .addColumn("name", "text", (col) => col.notNull())
        .addColumn("sort_name", "text", (col) => col.notNull())
        // …every other column and constraint
        .modifyEnd(sql`strict`),
    // New or changed columns, as expressions over the old table
    copy: { sort_name: sql`name` },
  })
}
```

It follows SQLite's recipe ([design §5.3](../design/1_introduction.md#53-changing-an-existing-table), with [Appendix B](../design/1_introduction.md#appendix-b-the-table-rebuild-needs-two-more-steps)):
1. It creates the new definition under a temporary name, `new_<table>`.
2. It copies the rows. Columns both definitions share are copied as they are, `copy` fills new or changed ones, and any other new column gets its default.
3. It drops the old table and renames the new one. It turns `legacy_alter_table` on for the rename, because other tables' triggers name the dropped table and would make the rename fail.
4. It recreates the table's indexes and triggers from their old SQL.
5. It puts back the `AUTOINCREMENT` counter, which the copy lowers to the highest id left. Otherwise ids of deleted rows would be reused.

Using it:
- **Indexes and triggers** come back exactly as they were. To change one, or if it uses a column that's gone, drop it before `rebuildTable()` and create the new version after.
- **Other tables** keep working. Their foreign keys and triggers name the table, so they apply to the new one. If one of them uses a column you renamed or removed, recreate it too.
- **Foreign keys:** it only runs with foreign keys off, as the runner sets them, and throws otherwise. Rows that break a foreign key fail the runner's `foreign_key_check`, and the whole migration rolls back.
- **Don't change its behavior.** Committed migrations call it, and they must keep doing what they did. Add options instead.

### Generated DB types

`src/repo/db_types.ts` is generated from the database, and is committed. `.kysely-codegenrc.json` overrides two columns with string unions: `files.type` and `releases.release_date_precision`. Never edit the file by hand. Regenerate it by running a migration (or rolling one back).

### Seeds

`npm run db:seed` loads `priv/repo/seeds.ts`: two releases, with their artists, labels, formats and media. There are no files or tracks, because those need real files on disk. It skips a database that already has releases. `npm run db:reset` starts over: it backs up and deletes the database, then migrates and seeds.

## GraphQL

- **The schema** is the SDL in `src/slunk_web/schema/*.graphql`, one file per context, and every file there is loaded. `schema.graphql` defines `Query`, `media.graphql` defines `Mutation`, and other files add to them with `extend type`. The SDL's descriptions document the API.
- **Resolvers** live next to their SDL (`media.ts`, `catalog.ts`), are typed with `Resolvers` from `resolvers_types.ts`, and are listed in `schema/index.ts`. They turn GraphQL ids into numbers before calling a context.
- **Context:** resolvers get the app (`db`, `dbPath`, and each context: `media`, `catalog`) and `loaders`.
- **Loaders:** the DataLoaders in `loaders.ts` batch a page's related rows into one query per relation (design §7.3): a release list's artists, labels, formats, media and covers are five queries, whatever the page size. Every relation a field resolves goes through one. They're made fresh for every request, so nothing is cached between requests.
- **Codegen:**
  - `codegen.ts` maps GraphQL types whose resolvers return a context type, through `mappers`: `File` is a `FileRecord`, `Release` a catalog `Release`, and so on. They're imported with a `Model` suffix, so their names don't clash with the generated ones.
  - The `ID` scalar accepts numbers as output, so resolvers can return the database's ids.
  - Arguments and input fields with a default are typed as always present (`avoidOptionals.defaultValue`), since GraphQL fills them in.
  - After changing a `.graphql` file, run `npm run codegen` here, and in `slunk-fe/` too, since the frontend's types come from the same files.
- **Ids:** a field called `id` must identify its object. Apollo Client caches objects by type and `id`, so two objects with the same `id` would be merged into one. So:
  - `FileUse` names the id of the release, artist or track that uses a file `entityId`;
  - `Credit` has no id, since release and track credits come from two tables whose ids overlap;
  - release formats, release media and credit roles are three types (`ReleaseFormat`, `ReleaseMedium`, `CreditRole`) behind one `ListItem` interface, so format 1 and medium 1 stay apart.
- **Lists** take `page`, `perPage` (at most 200), `sort` (a column, `-` in front for descending), `q` and filters, and return `{ items, total }`. Pickers use the same queries with `perPage: 20`.
- **The API:**
  - `health`: the database's absolute path, and the latest applied migration.
  - `files`, `file`, `fileCounts`: registered files. `files(withoutTrack: true)` leaves out tracks' audio, for creating tracks.
  - `folder`, `folderFiles`: the library on disk.
  - `registerFiles`, `updateFile`, `deleteFile`: changes to the file records.
  - `artists`, `artist`, `labels`, `label`, `releases`, `release`, `tracks`, `track`, `listItems`, `listItem`: the catalog. `releases` filters by `format`, `medium`, `label` and `artist`, and `releasesTitled` finds releases with a title.
  - `createArtist`, `updateArtist`, `deleteArtist`, and the same for labels, releases, tracks and list items.
  - `setReleaseTracks`, `setReleaseFiles`, `setReleaseCredits`: a release's edit tabs. Files can be given by path, and they're registered first.
  - `catalogTotals`: the dashboard's numbers.
  - `releaseSuggestion`, `trackSuggestions`: the import's prefill.
- Opening `http://127.0.0.1:4000/graphql` in a browser shows Apollo Sandbox, for trying queries.

## Conventions

### TypeScript

Node runs the code by stripping its types, which shapes the TypeScript settings:
- **`erasableSyntaxOnly`:** no `enum`, `namespace` or parameter properties.
- **`verbatimModuleSyntax`:** use `import type` for types.
- **Imports:** relative, ending in `.ts` (`./db.ts`). There's no path alias, since Node wouldn't resolve it.
- **`strict`**, and `tsc` only typechecks (`noEmit`).

File names are `snake_case`, as in Phoenix.

### Formatting and linting

- **Prettier:** the same settings as `slunk-fe`, without the Tailwind plugin. Run `npm run format`.
- **ESLint:** the recommended JavaScript and typescript-eslint rules, with Node globals. Run `npm run lint`.

Both skip the generated files.

### Install scripts

`package.json` lists packages under npm's `allowScripts`:
- `better-sqlite3` is allowed, because its install script fetches the native binary.
- `@apollo/protobufjs` is denied, because its script only prints warnings.
